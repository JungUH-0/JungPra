1차 실행만 보면 Keras는 56.1%→52.1%로 하락, PyTorch는 54.5%→59.2%로 상승해 정반대로 보였다. 그러나 각 조건을 2회씩 돌린 결과 Keras 쪽 하락은 실행 편차였고(평균 54.3% 대 54.4%로 동일), PyTorch 쪽 상승만 실재했다(평균 53.6% → 60.6%, +7.0%p). 자세한 내용은 "재현 실행" 섹션 참고.
가설 — 헤드 구조 차이 두 CNN의 분류 헤드가 실제로는 달랐음: Keras는 Flatten→Dropout(0.5)→Dense(11), PyTorch는 Flatten→Linear(128)→ReLU→Linear(11)로 Dropout이 아예 없음. 정규화가 부족했던 PyTorch에서는 weight decay가 그 빈 자리를 채워 개선된 반면, 이미 Dropout(0.5)이 있던 Keras에서는 정규화가 더해지는 효과보다 patience를 7로 늘려 과적합할 시간이 길어진 쪽이 크게 작용(train-val 격차 6.8%p→17.3%p 악화)한 것으로 보임.
한계 — ① 각 조건 단일 실행이라 위 해석은 가설 수준. ② 옵티마이저·스케줄러·patience 3가지를 동시에 바꿔 원인을 하나로 특정할 수 없음(통제변수 위반). ③ Keras 1차 시도(49.9%)는 EarlyStopping patience(3)가 ReduceLROnPlateau patience(2)와 너무 가까워, 학습률을 낮춘 바로 그 epoch에 종료되며 감소 효과를 전혀 못 쓴 설정 실수였음.
디버깅 뒷이야기 — PyTorch 첫 시도는 36.5%로 Keras(56.1%)와 19.6%p나 벌어졌는데, 원인은 두 가지였음: ① Conv→BatchNorm→ReLU 순서가 Keras(Conv→ReLU→BatchNorm)와 달랐음, ② EarlyStopping patience=3이 BatchNorm의 running stats가 안정화되기 전에 학습을 멈춰버림. 순서 통일 + patience=5로 재실행하니 54.5%로 격차가 1.6%p까지 줄어듦 — 프레임워크 무관 가설이 다시 확인됨.

가중치 초기화 — He vs Glorot

3 Conv 실험에서 Keras에만 he_normal을 명시한 이유
왜 시작값이 중요한가

학습 전 가중치는 랜덤값으로 채워지는데, 그 크기가 너무 크면 층을 지날 때마다 값이 증폭돼 기울기 폭발, 너무 작으면 0에 수렴해 기울기 소실이 일어남. 층마다 곱해지는 효과라 깊어질수록 심해짐 — 2 Conv에선 무시할 만했지만 3 Conv로 넘어가며 챙긴 이유.

He가 Glorot보다 2배 큰 이유

Glorot/Xavier는 활성함수가 신호를 그대로 통과시킨다고 가정하지만, ReLU는 음수를 전부 0으로 만들어 신호의 절반을 죽임. He는 이 손실분을 미리 보상해 가중치를 더 크게 잡음.

프레임워크 기본값이 다름

Keras Conv2D/Dense의 기본값은 Glorot이라 ReLU를 쓸 때 kernel_initializer="he_normal"을 직접 지정해야 함. PyTorch의 nn.Conv2d/nn.Linear는 기본값이 이미 Kaiming(He) 계열이라 코드 변경 없이 적용돼 있었음.

초기화표준편차전제KerasPyTorch
Glorot / Xavier√(1 / 입력수)활성함수가 신호를 보존기본값명시 필요
He / Kaiming√(2 / 입력수)ReLU가 신호 절반을 죽임he_normal 명시 필요기본값
즉 3 Conv 실험의 두 코드는 서로 다른 설정을 한 게 아니라, 같은 He 초기화에 도달하기 위해 각자 다른 조치를 한 것 — Keras는 기본값을 덮어썼고 PyTorch는 기본값을 그대로 뒀음. 전체 기록표에서 PyTorch 행이 "기본(He)"로 표기된 이유.

데이터 증강 기법

CNN + 증강 실험부터 적용, 값 자체도 하이퍼파라미터로 취급
RandomFlip — 좌우 뒤집기

Keras RandomFlip("horizontal") / PyTorch RandomHorizontalFlip(). 음식이 항상 같은 방향으로 놓여있다는 편향을 줄임.

RandomRotation — 회전

Keras RandomRotation(0.1)(±36°) / PyTorch RandomRotation(10)(±10°). 촬영 각도가 다른 사진에도 강건하게 만듦.

RandomZoom — 확대/축소 10%

Keras RandomZoom(0.1)만 적용. 음식이 화면을 꽉 안 채워도 인식하도록 도움.

알아두어야 할 점 — 두 프레임워크의 증강 설정이 완전히 동일하진 않음: ① Keras는 Flip+Rotation+Zoom 3종, PyTorch는 Flip+Rotation 2종만 적용(Zoom 미포함). ② Keras의 RandomRotation(factor)는 2π의 비율(0.1→±36°)이고 PyTorch의 RandomRotation(degrees)는 각도 직접 지정(10→±10°)이라, 같은 숫자 "0.1"과 "10"이 실제로는 다른 강도의 회전을 의미함. 그럼에도 최종 결과(56.1% vs 54.5%)가 근접했던 건 이 정도 차이가 성능에 큰 영향을 안 줬다는 뜻으로 해석 가능.
고려했지만 사용 안 한 기법효과
Translation (이동)음식이 항상 정중앙에 있다는 편향 완화
Brightness/Contrast (밝기·대비)촬영 조명 환경 차이에 강건해짐
Random Crop (일부 확대)음식이 화면 전체를 안 채워도 인식
Random Erasing (일부 지우기)특정 부위에만 의존하지 않게 강제
시간 제약상 Flip·Rotation·Zoom 3종으로 한정 — 이미 50.9%→56.1% 개선 효과가 확인돼 우선순위가 더 높은 다른 레버(옵티마이저, 구조)에 집중.

정리된 결론

구조가 곧 성능이다

ANN(21%) → DNN(27%) → CNN(44%). 같은 데이터, 같은 5 epoch에서 구조를 바꾼 것만으로 정확도가 두 배 넘게 뛰었다. 이미지에서 위치 정보를 보존하는 CNN의 우위가 숫자로 확인됨.

깊을수록 Adam, 얕을수록 SGD

ANN에선 SGD가 Adam을 압도(21% vs 13%)했지만, CNN에선 반대(Adam 44% vs 모멘텀 없는 SGD 21~26%). 모델이 복잡해질수록 적응형 옵티마이저의 이점이 커짐.

모멘텀 하나로 +12%p

CNN + SGD에 momentum 0.9만 추가했을 뿐인데 정확도가 20~25% → 32~38%로 뛰었다. 순정 SGD는 복잡한 손실 지형에서 5 epoch로는 사실상 정체됨.

더 학습해도 안 느는 건 시간이 아니라 구조 문제

Keras CNN+Adam을 5→15 epoch로 늘리자 train acc는 71%→93%로 뛰었지만 test acc는 43.6%→45.4%로 거의 그대로. 초과 학습은 과적합만 키우고, Dropout 비율 상향이나 데이터 증강 같은 별도 대책이 필요함.

Adam은 빠르게, SGD+momentum은 건강하게

PyTorch SGD+momentum을 5→15 epoch로 늘리자 정반대로 val/test acc가 같이 오르고 loss도 낮아짐(1.94→1.65). 15 epoch 만에 Adam(5 epoch) 수준의 정확도를 따라잡으면서 loss는 Adam(15 epoch, 2.93)보다 훨씬 낮음 — 느리지만 과적합에 강한 수렴.

구조 개선은 여전히 남은 지렛대였다

옵티마이저·정규화를 다 맞춘 뒤에도 Conv 블록 추가 + BatchNorm + He 초기화로 50.9% → 56.1%까지 더 올랐다. 하이퍼파라미터 튜닝과 구조 개선은 서로 대체재가 아니라 누적되는 별개의 지렛대라는 뜻. 단, 재현 실행에서 이 조건이 52.5%로 나와 개선폭은 +5.2%p가 아니라 +1.6~3.4%p로 봐야 한다(재현 실행 섹션 참고).

정규화는 더할수록 좋은 게 아니라 "총량"의 문제다

각 조건을 2회씩 돌린 결과, AdamW는 Dropout이 없던 PyTorch에서 53.6% → 60.6%(+7.0%p)를 만들었고 이미 Dropout(0.5)이 있던 Keras에서는 54.3% → 54.4%로 아무 차이도 없었다. PyTorch의 AdamW 두 실행이 Adam 두 실행보다 모두 높아 범위가 겹치지 않는다. 기법 자체의 우열이 아니라 모델에 이미 걸린 정규화 총량의 문제 — 부족한 곳은 채우고, 충분한 곳에는 보탤 것이 없다.

torch33 Conv+BN · AdamW+ReduceLR · ES p=7— → 93.359.7 → 59.759.2 → 61.91.32 → 1.302.7%p
keras1 — 1.8%p 안에서 재현 세 정확도 지표가 모두 2%p 미만으로 일치했다. 그동안 "1~2%p 차이는 노이즈로 봐야 한다"고 해석해온 근거가 추정이 아니라 실측이 됐다. 동시에 Val이 1.8%p나 움직였다는 사실 자체가, DNN 단계에서 Keras와 PyTorch의 승자가 엇갈렸던 것(26.9% vs 25.6%, 1.3%p 차)을 프레임워크 차이로 읽으면 안 되는 이유이기도 하다.
keras1 곡선이 추가로 보여준 것 — 검증 손실이 3 epoch에서 1.71로 최저를 찍고 이후 3.35까지 단조 상승했다. 학습 손실은 같은 구간에서 0.18까지 내려간다. 표의 최종 숫자만으로는 격차의 크기만 알 수 있지만, 곡선은 과적합이 시작된 지점이 3 epoch이라는 것까지 특정해준다.
keras2 — 3.6%p 편차, 기존 결론 하나에 영향
Test가 56.1% → 52.5%로 3.6%p 떨어졌다. 이 수치는 "구조 개선(3 Conv + BatchNorm + He)이 50.9% → 56.1%로 +5.2%p를 만들었다"는 기존 서술의 근거였다. 재현값을 쓰면 개선폭이 +1.6%p, 두 실행 평균(54.3%)으로 보면 +3.4%p가 된다. 방향은 여전히 양(+)이지만 처음 주장한 +5.2%p보다 작고 덜 확실하다고 고쳐 말해야 한다.
왜 keras1(1.8%p)보다 두 배로 흔들렸나 — 검증 곡선이 눈에 띄게 들쭉날쭉하다(0.375 → 0.503 → 0.468 → 0.497). keras1의 평평한 검증선과 대조적이다. 여기에 EarlyStopping이 얹히면 편차가 두 겹으로 쌓인다: ① 가중치 초기화 차이, ② 어느 epoch에서 멈추고 어느 가중치를 복원할지가 달라짐(1차 17 epoch, 2차 19 epoch). BatchNorm이 검증 지표를 흔들고, 그 위에서 patience=3이 최고점을 고르니 뽑히는 지점이 실행마다 바뀐다 — 앞서 정리한 BatchNorm↔EarlyStopping 상호작용이 정확도 편차로 드러난 사례.
덧붙여 — 19 epoch 시점에도 검증 정확도는 상승 중이었다(0.4851 → 0.4977). val_loss 기준으로 멈춘 탓에 더 갈 수 있었는데 잘린 정황이 있다.
keras3 — 4.6%p 편차, 결론 하나가 무너짐
Test가 52.1% → 56.7%로 4.6%p 올랐다(지금까지 최대 편차). 이 수치는 "Keras에서는 AdamW가 56.1% → 52.1%로 4%p 떨어뜨렸다"는 서술의 근거였다. 재현값까지 넣어 평균 내면:
keras2(Adam) 56.1 · 52.5 → 평균 54.3%  |  keras3(AdamW) 52.1 · 56.7 → 평균 54.4%
두 조건이 사실상 동일하다. 1차 실행에서 우연히 keras2가 높은 쪽, keras3가 낮은 쪽에 걸렸던 것이고, "AdamW가 Keras에서 해로웠다"는 관찰은 실행 편차였다고 보는 것이 맞다.
결론 ②에 미치는 영향 — "정규화는 총량의 문제"의 근거는 PyTorch +4.7%p / Keras −4.0%p라는 대칭이었는데, 그중 Keras 쪽이 사라졌다. PyTorch 쪽(torch2·torch3 재현)의 결과에 따라 이 결론의 유지 여부가 결정된다.
torch2 — 결론 ②의 판정이 torch3 하나에 걸렸다
Test는 54.5% → 52.6%로 1.9%p 차이지만 Val이 6.1%p 움직여 지금까지 최대 편차다. 결론 ②의 PyTorch 쪽 근거를 재현값까지 넣어 정리하면:
PyTorch Adam 54.5 · 52.6 → 평균 53.6%  |  PyTorch AdamW 59.2 · 61.9 → 평균 60.6%
torch3가 57% 이상이면 Adam 대비 +4%p 이상이 남아 결론 ②가 "PyTorch처럼 정규화가 부족한 모델에서만 유효"로 좁혀져 생존한다. 55% 이하면 차이가 편차 범위에 들어가 폐기해야 한다.

결론 ②는 이렇게 다듬어진다 — 원래 서술이던 "프레임워크마다 정반대로 작용한다"에서 "정규화가 부족한 모델에서는 +7%p를 만들고, 이미 Dropout이 있던 모델에서는 아무 차이도 없었다"로. "Keras에서 해로웠다(−4.0%p)"는 부분은 노이즈였지만 핵심은 살아남았고, 근거는 오히려 단단해졌다. 여기에 torch1 A/B에서 PyTorch가 train 99.4%까지 암기한 사실이 "정규화가 부족했다"는 전제의 직접 증거로 붙는다.

torch2 곡선이 드러낸 문제 — EarlyStopping이 손해를 봤다
epoch 5 : val_loss 1.494(최저) · val_acc 51.2%  ←  복원된 가중치
epoch 8 : val_loss 1.500 · val_acc 54.7%  ←  실제 최고 정확도
val_loss가 0.006 차이로 밀려 val 정확도 3.5%p를 잃었다. monitor="val_loss"로 최적 시점을 고른 결과다. BatchNorm 정리 문서에 "val_loss 대신 val_accuracy를 모니터링하라"고 적어둔 조언이 일반론이 아니라 이 실험 데이터로 확인된 사례가 됐다.
