# CGI 색상환(상의 색 변경) 정리

정리한 날: 2026-10-21 (오후 반영) · 기준 코드: 팀 저장소 moa(`CGI_MOA`) · 실험 위치: `D:/JungPra/pythonpra/moalocal`

## 한눈에

- **무엇**: 상의를 입힌 합성 결과에서 **새로 입힌 상의만** 색을 바꿔 보는 기능. 원형 색상환에서 **색 하나만** 고른다.
- **왜**: 퍼스널컬러 흐름(상의 피팅 → 옷 색 변경 → 관광지 배경 → 배경에 맞는 옷)의 두 번째 단계. 진단 모델 없이도 혼자 동작한다.
- **지금 상태**
  - 단색 옷: 동작 확인됨
  - 무늬 옷: **무늬째로 색조를 바꾸는 방식**으로 해결했다. 기본은 '한 색 계열로'(무늬 색이 고른 색 쪽으로 반쯤 따라옴)
  - 엠블렘 · 로고: 원래 색으로 남기는 '작은 무늬 보호'를 넣었다
  - 시험 페이지와 moa 복사본의 색 변경 팝업 양쪽에 반영했다. 팝업은 10-21 켜서 확인했다
- **팀 저장소 영향**: 없음. 모든 작업은 moalocal 안에서 했고, 이 폴더는 Git에서 빠져 있다. CGI_MOA는 변경 0건이다.

## 1. 정한 방향

| 날짜 | 결정 |
|---|---|
| 10-19 | **색상환 색 바꾸기를 먼저** 만든다. 진단이 없어도 혼자 동작하는 기능이다 |
| 10-19 | **퍼스널컬러는 사용자가 직접 고른다** (봄웜 · 여름쿨 · 가을웜 · 겨울쿨). 고른 계절의 추천 색을 색상환 위에 표시한다. 이미 진단받아 온 사람이 많아서 흐름이 자연스럽고, 진단 모델도 필요 없다 |
| 10-19 | **계절별 추천 색은 우리가 설정값(표)으로** 넣는다. 출처 하나를 정해 계절마다 6~8색을 정하고, **밝기까지 포함**한다 |
| 10-19 | **진단 모델은 나중에** '직접 고르기' 자리에 끼우는 확장으로만 다룬다 |
| 10-21 | 무늬 옷은 **색 하나만 고르면 무늬째로 바뀌게** 한다. 묶음을 하나씩 고르는 방식은 불편하고, 사진에서 누르는 방식은 꽃무늬처럼 작은 곳을 고르기 힘들어서 뺐다 |
| 10-21 | 무늬 옷 기본은 **'한 색 계열로'**. '무늬 대비 유지'는 형광 느낌이 강해서 버튼으로만 남긴다 |
| 10-21 | 엠블렘 · 로고는 비슷한 계열 색이라도 **바뀌지 않아야** 한다 |

## 2. 동작 방식

| 단계 | 방법 |
|---|---|
| 상의 영역 | 합성 결과 사진에서 SAM2로 새 상의를 찾는다. 기존 입힐 영역은 힌트(감싼 박스 + 3% 여유)로만 쓴다. 찾은 크기가 입힐 영역의 0.3~2배를 벗어나면 실패로 본다 (dev-cej `restore.find_garment`와 같은 방식) |
| 색 고르기 | 원형 색상환(각도 = 색상, 중심에서 거리 = 진하기) + 밝기 막대. 단색 · 무늬 모두 색 하나만 고른다 |
| 색 묶음 | 상의 화소를 색이 비슷한 것끼리 최대 4묶음으로 나눈다(k-평균). 그림자처럼 같은 색인데 밝기만 다른 묶음, 줄무늬 경계의 중간색 묶음은 합친다. 묶음이 1개면 단색 옷으로 본다 |
| 단색 옷 | 밝기는 원래 명암 차이를 그대로 두고(L = 고른 L + (화소 L − 평균 L)), 색은 고른 색 + 원래 색 차이의 절반으로 옮긴다 |
| 무늬 옷 | 가장 넓은 묶음(대표색)이 고른 색이 되도록 옷 전체를 옮긴다. 밝기는 대표색 → 고른 밝기로 순서가 뒤집히지 않게 늘이거나 줄이고, 색은 대표색 → 고른 색만큼 돌린 뒤 고른 색 쪽으로 반쯤 섞는다('한 색 계열로'). 보색에 가까운 무늬일수록 차분해진다 |
| 작은 무늬 보호 | 어느 묶음에도 안 맞는 색이 좁은 곳(옷의 3% 미만)에 모인 덩어리를 찾아, 안쪽까지 채워 원래 색으로 둔다. 엠블렘 · 로고 · 작은 글자가 여기에 걸린다 |
| 경계 | 상의 테두리는 3×3 평균 비율로 원래 색과 섞는다 |
| 계산 위치 | 브라우저 안에서만. 서버는 상의 윤곽만 찾아 준다. 사진 1장 준비(묶음 · 보호 포함) 0.6~1.1초 |
| 안내 | 고른 색이 원래 상의(무늬 옷은 대표색)보다 밝기(L)가 35 넘게 밝으면 "주름 · 명암이 약하게 보일 수 있음" 문구를 띄운다 |

## 4. 문제점

| 문제 | 내용 |
|---|---|
| **색 바꾼 결과를 저장하지 않음** | 바뀐 색은 팝업 화면에서만 보인다. 결과 화면의 '저장'은 색을 바꾸기 전 합성 결과를 저장한다 |
| 어두운 옷 → 밝은 색 | 검정 옷은 명암 정보가 적어 밝은 색으로 바꾸면 평평하게 보인다. 여름쿨처럼 밝은 계절에서 특히 눈에 띌 수 있다 |
| 자동 윤곽 실패 | 윤곽이 잘못 잡히면 팝업에 오류 문구만 나오고, 손으로 고칠 수단이 없다 |
| 합성 단계 흠도 같이 칠해짐 | 상의 입히기에서 생긴 흠이 윤곽에 들어가면 같이 칠해진다. 꽃무늬 실험에서도 소매 끝 하얀 테두리, 모델 2 오른팔 옆 가는 갈색 세로선(restore 뒤에 생김, 원인 확인 안 함)이 나왔다 |
| AnyDoor 무늬 자체 | 입힌 무늬가 원래 옷과 다르게 그려진다 (꽃무늬: 꽃이 커지고 잎이 청록). 색 변경으로는 해결되지 않는다 |
| 작은 무늬 보호의 한계 | 기준값을 6장으로만 맞췄다. 중간 회색 옷 위의 검정 로고는 그림자와 구분이 안 돼 보호되지 않을 수 있다 |
| 무늬 색이 뜻밖일 수 있음 | 무늬 색은 대표색을 따라 같이 움직여서, 고른 색에 따라 예상과 다른 색이 나올 수 있다. '무늬 대비 유지'에서 더 심하고(연두 → 빨강 줄이 청록), 대표색이 옅은 옷에 진한 색을 고르면 다른 무늬가 진해진다 |
| 팝업 앱에는 restore 없음 | moa 복사본은 main 기준이라, 팝업에서 보는 결과는 restore 적용 전 합성 결과다 |
| 메모리 | 백엔드 실행 때 AnyDoor 가중치(16.8GB)를 mmap으로 읽게 했다. 가상 메모리 여유가 가중치보다 작아서 넣은 대책이고, 꼭 필요한지는 확인하지 않았다 |

## 5. 다음 단계 (제안)

1. **계절 고르기 + 추천 색 표시**: 추천 색 표의 출처를 정하고, 색 점을 누르면 밝기 막대도 같이 움직이게 한다. 무늬 옷은 지금 방식 그대로 대표색이 그 색이 된다.
2. **색 바꾼 결과 저장**: 필요하면 '이 색으로 저장'을 추가한다. 새 결과로 저장할지, 원래 결과를 덮어쓸지는 정해야 한다.
3. **더 많은 옷으로 검증**: 작은 무늬 보호와 색 묶음 기준값을 로고 · 글자 · 체크무늬 등 다른 옷으로 확인한다.
4. **팀 저장소 반영**은 팀 결정이 필요하다. 넣을 것은 API 1개와 화면 컴포넌트 1개이고, 브랜치 → PR 순서로 한다. 팀 기본 설정(mock 모드)에서는 새 API가 없으므로 가짜 응답을 넣거나 버튼을 숨겨야 한다.
