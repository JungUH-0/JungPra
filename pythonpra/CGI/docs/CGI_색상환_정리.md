# CGI 색상환(상의 색 변경) 정리

정리한 날: 2026-10-21 · 기준 코드: 팀 저장소 moa(`CGI_MOA`) · 실험 위치: `D:/JungPra/pythonpra/moalocal`

## 한눈에

- **무엇**: 상의를 입힌 합성 결과에서 **새로 입힌 상의만** 색을 바꿔 보는 기능. 원형 색상환에서 색을 고른다.
- **왜**: 퍼스널컬러 흐름(상의 피팅 → 옷 색 변경 → 관광지 배경 → 배경에 맞는 옷)의 두 번째 단계. 진단 모델 없이도 혼자 동작한다.
- **지금 상태**
  - 시험 페이지: 동작 확인됨
  - moa 복사본 연결: 결과 화면 '색 변경' 버튼까지 연결됨. 10-20 직접 실행해 봤고, **무늬 있는 상의에서 문제** 확인
- **팀 저장소 영향**: 없음. 모든 작업은 moalocal 안에서 했고, 이 폴더는 Git에서 빠져 있다. CGI_MOA는 변경 0건이다.

## 1. 정한 방향 (10-19)

1. **색상환 색 바꾸기를 먼저** 만든다. 진단이 없어도 혼자 동작하는 기능이다.
2. **퍼스널컬러는 사용자가 직접 고른다** (봄웜 · 여름쿨 · 가을웜 · 겨울쿨). 고른 계절의 추천 색을 색상환 위에 표시한다. 이미 진단받아 온 사람이 많아서 흐름이 자연스럽고, 진단 모델도 필요 없다.
3. **계절별 추천 색은 우리가 설정값(표)으로** 넣는다. 자동으로 생기는 값이 아니다. 출처 하나를 정해 계절마다 6~8색을 정하고, **밝기까지 포함**해야 한다(계절 차이는 밝기에서 크다).
4. **진단 모델은 나중에** '직접 고르기' 자리에 끼우는 확장으로만 다룬다.

## 2. 동작 방식

| 단계 | 방법 |
|---|---|
| 상의 영역 | 합성 결과 사진에서 SAM2로 새 상의를 찾는다. 프롬프트는 입힐 영역을 감싼 박스 + 3% 여유. 찾은 크기가 입힐 영역의 0.3~2배를 벗어나면 실패로 본다 (dev-cej `restore.find_garment`와 같은 방식) |
| 색 고르기 | 원형 색상환(각도 = 색상, 중심에서 거리 = 진하기) + 밝기 막대 |
| 색 바꾸기 | 상의 화소를 LAB로 바꿔 계산한다. 밝기는 원래 명암 차이를 그대로 두고(L = 고른 L + (화소 L − 평균 L)), 색은 고른 색 + 원래 색 차이의 절반으로 옮긴다. 경계는 3×3 평균 비율로 섞는다 |
| 계산 위치 | 브라우저 안에서만. 서버는 상의 윤곽만 찾아 준다 |
| 안내 | 고른 색이 원래 상의보다 밝기(L)가 35 넘게 밝으면 "주름 · 명암이 약하게 보일 수 있음" 문구를 띄운다 |

## 3. 만든 것

### 3-1. 시험 페이지 — `moalocal/colorwheel/`

- 라이브러리 없는 페이지 1장 + 예시 2장. 상의 입히기 결과는 restore 적용 후 사진이다.
  - F01: T01 회색 헨리넥 (평균 밝기 L 51.5)
  - F07: T02 검정 크롭티 (평균 밝기 L 24.9)
- 확인 결과
  - F01 → 파랑 #5253FF, 밝기 35%에서 남색 #1D1D59: 정상
  - F07 → 분홍 #FF79EA: 동작하고 밝기 안내 문구도 뜸
  - 콘솔 오류 없음
- 켜기: 런치 설정 `moalocal-colorwheel` → http://localhost:7880

### 3-2. moa 복사본 연결 — `moalocal/moa_app/`

- 흐름: 합성 → 결과 화면 **'색 변경'** 버튼 → 색 변경 팝업. 처음 누를 때만 SAM2로 윤곽을 찾고, 찾은 윤곽은 저장해 두고 다시 쓴다.
- 바꾼 파일 (복사본 안에서만)

| 파일 | 내용 |
|---|---|
| `backend/routers/results.py` | `POST /api/results/{id}/garment-mask` 추가 (결과의 새 상의 윤곽, `{id}_garment.png` 로 저장) |
| `frontend/src/studio/ColorWheel.jsx` | 새 파일. 색 변경 팝업 (색상환 · 밝기 · 원래 색으로 · 누르는 동안 원래 결과) |
| `frontend/src/pages/Studio.jsx` | 결과 화면 '색 변경' 버튼 |

## 4. 문제점

| 문제 | 내용 |
|---|---|
| **무늬가 뭉개짐** | 상의 전체를 한 가지 색으로 보고 평균 색만 옮기기 때문에, 무늬 색끼리의 차이가 줄어 한 색으로 뭉개진다 (10-20 실행에서 확인) |
| **색 바꾼 결과를 저장하지 않음** | 바뀐 색은 팝업 화면에서만 보인다. 결과 화면의 '저장'은 색을 바꾸기 전 합성 결과를 저장한다. 팝업을 닫으면 바꾼 색은 사라진다 |
| 어두운 옷 → 밝은 색 | 검정 옷은 명암 정보가 적어 밝은 색으로 바꾸면 평평하게 보인다. 여름쿨처럼 밝은 계절에서 특히 눈에 띌 수 있다 |
| 자동 윤곽 실패 | 윤곽이 잘못 잡히면 팝업에 오류 문구만 나오고, 손으로 고칠 수단이 없다 (시험 때 F07은 점을 찍어 다시 잡음) |
| 합성 단계 흠도 같이 칠해짐 | 상의 입히기에서 생긴 흠(F01 몸통 왼쪽 흰 띠)이 윤곽에 들어가면 그대로 같이 칠해진다 |
| AnyDoor 무늬 자체 | 입힌 무늬가 원래 옷과 다르게 그려진 경우는 색 변경으로 해결되지 않는다 |
| 메모리 | 백엔드 실행 때 AnyDoor 가중치(16.8GB)를 mmap으로 읽게 했다. 당시 가상 메모리 여유가 15.8GB여서 넣은 대책이고, 꼭 필요한지는 확인하지 않았다 |

## 5. 다음 단계 (제안)

1. **무늬별 색 지정**: 영역을 다시 고르게 하지 않고 **색 묶음 자동 나누기**로 한다.
   - 상의 화소를 색(a, b)으로만 나눈다. 밝기를 빼야 그림자 진 같은 색이 갈라지지 않는다.
   - 바탕 · 줄무늬 · 로고 같은 색 견본을 보여 주고, 견본을 고른 뒤 색상환에서 새 색을 고르게 한다.
   - 잘못 나뉜 곳만 브러시로 고친다 (moa 다듬기 팝업 방식).
   - 더 간단한 대안: 바탕색만 바꾸고 무늬는 그대로 두기.
2. **색 바꾼 결과 저장**: 필요하면 '이 색으로 저장'을 추가한다. 새 결과로 저장할지, 원래 결과를 덮어쓸지는 정해야 한다.
3. **계절 고르기 + 추천 색 표시**: 추천 색 표의 출처를 정하고, 색 점을 누르면 밝기 막대도 같이 움직이게 한다.
4. **팀 저장소 반영**은 팀 결정이 필요하다. 넣을 것은 API 1개와 화면 컴포넌트 1개이고, 브랜치 → PR 순서로 한다.

### 계절별 추천 색의 방향 (설정값 표를 만들 때 기준)

| 계절 | 색 기운 | 밝기 | 선명도 |
|---|---|---|---|
| 봄웜 | 노란 기운 | 밝음 | 선명 |
| 여름쿨 | 푸른 기운 | 밝음 | 탁하고 연함 |
| 가을웜 | 노란 기운 | 어두움 | 차분함 |
| 겨울쿨 | 푸른 기운 | 대비 큼 | 선명 |
