### 기사 열 (DB 조회 결과·CSV 백업 공통)

| 열 | 뜻 |
|---|---|
| `keyword` | 걸린 키워드. 여러 개면 `삼성전자\|SK하이닉스` |
| `title` | 기사 제목 |
| `label` | positive / neutral / negative (세 확률 중 가장 큰 것) |
| `score` | label의 확률. **감성 세기가 아니라 확신도** |
| `p_positive`, `p_neutral`, `p_negative` | 세 라벨 각각의 확률 (합 1) |
| `sentiment_index` | p_positive − p_negative. −1(부정) ~ +1(긍정) |
| `collected_at` | 수집 시각 |
| `link` | 기사 주소. 중복 판단 기준. 항상 마지막 열 |

| 경로 | 내용 |
|---|---|

### 9/23 · 감성지수

- 문제: `score`는 모델이 고른 라벨의 확신도라서, `negative 0.99`와 `positive 0.99`가 같은 값. 이를 평균 낸 `avg_score`는 분위기 지표로 쓸 수 없음
- 해결
  - 모델에서 세 라벨 확률을 모두 받음 (`top_k=None`)
  - `sentiment_index = p_positive − p_negative` 저장
  - API의 `avg_score`는 `avg_confidence`로 이름을 바꾸고 `avg_sentiment_index` 추가
  - 기존 172건은 저장된 제목으로 모델을 다시 돌려 채움. 다시 돌린 라벨이 기존 라벨과 다른 기사 0건
- 판정 기준·표시 규칙은 "뉴스 감성 산정 기준" 문서로 정리 (색: 긍정 빨강, 부정 파랑)

## 3. 뉴스 수집 2~3페이지 확장 (상세)

### 3-1. 왜 바꿨나

제목 필터를 넣은 뒤 표본이 크게 줄었다.

- 네이버 뉴스 검색 첫 화면은 기사 10개가 최대
- 그중 제목에 종목명이 있는 기사는 키워드당 보통 2~5개
- SK하이닉스는 8거래일 중 3일이 기사 5건 미만, 9/22는 기사 1건으로 감성지수가 −1.0

필터를 풀면 관련 없는 기사가 다시 섞이므로, **필터는 그대로 두고 후보를 늘리는 방향**으로 결정했다.
과정 조건상 API는 쓰지 않고 크롤링만으로 해결한다.

### 3-2. 처음 시도: 일반 검색 주소에 start 붙이기 (실패)

```
https://search.naver.com/search.naver?where=news&query=SK하이닉스&sort=1&start=11
```

`check_pages.py`로 start=1, 11, 21을 요청한 결과:

| 페이지 | 받은 제목 | 1페이지와 겹침 |
|---|---|---|
| start=1 | 10개 | - |
| start=11 | 10개 | 10개 |
| start=21 | 10개 | 10개 |

세 페이지 모두 같은 10개가 순서만 바뀌어서 왔다. **일반 검색 주소는 start 값을 무시한다.**
네이버 뉴스 검색은 스크롤을 내리면 기사를 이어 붙이는 방식이라, 처음 받는 HTML에는 첫 10개만 들어 있다.

### 3-3. 스크롤이 부르는 요청 찾기

Selenium으로 스크롤을 흉내 내는 대신, **스크롤할 때 브라우저가 보내는 요청을 직접 부르는 방법**을 택했다.

1. 크롬에서 네이버 뉴스 검색 → 최신순
2. F12 → Network → 필터 `Fetch/XHR`
3. 스크롤을 내려서 기사가 더 불러와질 때 새로 생기는 요청 확인

```
https://s.search.naver.com/p/newssearch/3/api/tab/more?...&query=sk하이닉스&sort=1&ssc=tab.news.all&start=21
```

스크롤할 때마다 `start`가 21, 31 ... 처럼 10씩 늘어난다.

### 3-4. 확인 결과 (`check_more_api.py`)

| 확인 항목 | 결과 |
|---|---|
| requests로 받아지나 | 상태코드 200, `application/json` |
| 응답 형식 | JSON 맨 위 키 `collection`, `url`. 기사 목록 HTML은 `collection[0].html` 안에 있음 |
| 제목 선택자 | 기존과 같은 `span.sds-comps-text-type-headline1`으로 10개 추출 |
| 필요한 값만 넣어도 되나 | 된다. 브라우저가 보낸 값을 다 채운 버전과 결과가 같음 |
| 1페이지 vs start=11 | 겹침 0 / 10 |
| start=11 vs start=21 | 겹침 1 / 10 (요청 사이에 새 기사가 올라와서 목록이 한 칸 밀림) |
| 세 번 요청으로 모은 서로 다른 기사 | 29개 (기존 10개 → 약 3배) |
| 날짜 지정 (`ds`, `de`, `nso`의 `p:from..to..`) | 9/29로 지정하면 9/29 기사가 나옴 |

필요한 최소 파라미터:

| 파라미터 | 값 | 뜻 |
|---|---|---|
| `ssc` | `tab.news.all` | 뉴스 탭 |
| `query` | 검색어 | |
| `sort` | `1` | 최신순 |
| `start` | `11`, `21`, ... | 몇 번째 기사부터 |
| `nso` | `so:dd,p:all,a:all` | 정렬·기간 옵션 (기간 전체) |

헤더는 `User-Agent`와 `Referer: https://search.naver.com/`를 같이 보낸다.

|---|---|
| `_fetch_page_html(keyword, page)` | 1페이지는 일반 검색 HTML, 2페이지부터는 스크롤 요청 JSON의 `html`을 모아서 돌려줌 |
| `search_candidates(keyword, pages)` | 페이지를 차례로 받아 (제목, 링크) 후보를 모음. 링크 기준으로 한 번만 담음 |
| `get_naver_news(keyword, count, min_hits, pages)` | 후보에 제목 필터 적용. 반환값이 `{"articles", "candidates", "pages"}` |
| `collect_many(..., pages=3)` | 키워드별 결과에 `candidates`(후보 수), `pages`(쓴 페이지 수) 추가 |

```
키워드마다
  1페이지  search.naver.com (HTML)                → 후보 10개
  3초 대기
  2페이지  s.search.naver.com ... start=11 (JSON)  → 후보 +10개
  3초 대기
  3페이지  s.search.naver.com ... start=21 (JSON)  → 후보 +10개 (밀린 1건은 링크로 걸러짐)
  → 제목 필터 → 키워드 합치기 → 새 기사만 감성분석 → 저장
```

안전장치:
- 어떤 페이지에서 새 기사가 하나도 안 나오면 그 키워드는 거기서 멈춘다.
- 스크롤 요청 응답이 JSON이 아니면 그 키워드는 1페이지 결과만 쓰고 다음 키워드로 넘어간다. (차단이 아니라 화면 변경으로 봄)
- 요청 사이 3~4.5초 무작위 대기 (키워드 사이도 포함). 일정한 간격으로 기계적으로 요청하는 모습이 덜 드러나게.
  한 번 수집할 때 요청은 키워드 3개 × 3번 = 9번, 약 30초.

### 3-6. 차단 감지와 요청 로그 (9/30 추가)

요청마다 `request_log.csv`에 한 줄씩 남긴다. 언제부터 막혔는지 확인하는 용도.

| 열 | 뜻 |
|---|---|
| `time` | 요청 시각 |
| `keyword`, `page` | 키워드, 몇 페이지째 |
| `source`, `start` | `search`(1페이지) 또는 `more`(스크롤 요청), start 값 |
| `status` | 상태코드. 네트워크 오류면 `ERR` |

차단 의심 조건과 동작:

| 조건 | 동작 |
|---|---|
| 상태코드 403, 429 | 남은 요청 전부 멈춤 |
| 제목을 하나도 못 받았고, 응답에 자동입력 방지 문구 (`captcha`, `자동입력`, `비정상적인 접근` 등) | 남은 요청 전부 멈춤 |
| 1페이지가 200인데 제목 0개 (차단 화면이거나 화면 구조 변경) | 남은 요청 전부 멈춤 |
| 네트워크 오류 | 남은 요청 전부 멈춤 |

- 멈추기 전까지 모은 기사는 정상적으로 저장한다.
- 제목을 정상으로 받았으면 차단이 아닌 것으로 본다. 정상 검색 페이지도 스크립트 안에 `captcha` 같은 단어가 들어 있어서, 처음에는 응답 전체에서 문구를 찾다가 정상 페이지를 차단으로 오인했다 (9/30 첫 실행에서 발견, 바로 수정).
- 남은 키워드는 요청하지 않고 "건너뜀"으로 표시한다.

가짜 응답으로 확인한 경우:

| SK하이닉스 1페이지 네트워크 오류 | 삼성전자 저장, SK하이닉스 0건, 코스피 건너뜀 |
| 코스피 2페이지가 JSON 아님 | 코스피는 1페이지만 쓰고 수집은 정상 종료 |

## 6. SQLite로 옮기기 (상세, 10/1)

### 6-1. 왜 옮겼나

- 교수님이 보고 싶은 건 수집 → 저장 → 조회 → 분석이 이어진 전체 파이프라인. CSV는 "저장"이 파일 쓰기라서 DB 연결 단계가 비어 있었다.
- CSV에서 직접 처리하던 것들이 DB에서는 기본 기능이 된다.
  - 같은 기사 두 번 저장 방지: CSV는 코드로 link 비교 → DB는 `link UNIQUE`
  - 한 기사에 키워드 여러 개: CSV는 `삼성전자|SK하이닉스` 문자열 → DB는 연결 테이블
  - 키워드 추가할 때 CSV는 파일 전체를 다시 씀 → DB는 한 줄 INSERT
  - 수집 중간에 실패하면 CSV는 깨질 수 있음 → DB는 한 회차를 한 번에 커밋(실패하면 통째로 취소)
  - 수집이 쓰는 동안 서버가 읽어도 됨 (WAL 모드)

### 6-2. 왜 SQLite인가

- 설치할 서버가 없다. 파이썬에 기본으로 들어 있고 DB가 파일 하나(`news.db`)
- 하루 4번 × 수십 건이면 몇 년 쌓여도 SQLite로 충분
- SQL은 표준이라 나중에 MySQL·PostgreSQL로 옮겨도 쿼리 대부분을 그대로 쓴다

### 6-3. 테이블

```
articles                      article_keywords            keywords
-----------------------       --------------------        -----------
id (PK)               <────── article_id (FK)        ┌──> id (PK)
link (UNIQUE)                 keyword_id (FK) ───────┘    name (UNIQUE)
title, label, score
p_positive, p_neutral, p_negative
sentiment_index
collected_at

request_logs
---------------------------------------------------------------
id, time, keyword, page, source, start, status, titles, new_titles, elapsed_ms, result
```

- 기사와 키워드는 다대다(한 기사가 여러 키워드, 한 키워드에 여러 기사)라서 연결 테이블로 나눴다.
- 조회 결과는 예전 CSV와 같은 열 구성으로 돌려준다(`db.articles_df`). 그래서 `start.py`, `validate_stock.py`의 계산 코드는 거의 그대로다.

### 6-4. 바뀐 코드

| 파일 | 바뀐 점 |
|---|---|
| `db.py` (새 파일) | 테이블 생성, 기사 저장·키워드 연결, 요청 로그 저장, 조회 |
| `collector.py` | 저장을 CSV → DB로. 요청 로그도 DB로. 감성분석은 DB를 잡지 않은 상태에서 먼저 돌리고 저장은 한 번에 커밋 |
| `collectall.py` | 끝에 DB 누적 건수 출력 |
| `start.py` | CSV 읽기 → DB 조회. 키워드별로 필요한 기사만 SQL로 가져옴. `/articles`는 정렬·개수 제한을 SQL에서 처리. `GET /db/status` 추가 |
| `validate_stock.py` | 뉴스를 DB에서 읽음 |
| `migrate_csv_to_db.py` (새 파일) | 기존 CSV → DB. 다른 CSV 합치기 |
| `export_db_to_csv.py` (새 파일) | DB → `backup/` CSV |

### 6-5. 확인한 것 (테스트 환경, 9/14 ~ 9/23 데이터 165건)

- 옮기기: 165건 저장, 키워드별 건수(삼성전자 70 / SK하이닉스 46 / 코스피 59)가 CSV와 같음. 두 번째 실행은 "이미 있음 165"로 변화 없음
- API 결과 비교: `/sentiment`, `/trend`, `/compare`, `/validate` 세 키워드 모두 CSV 때와 숫자까지 같음. `/articles`는 같은 기사·같은 순서(수집 시각이 같은 기사끼리는 순서가 바뀔 수 있음)
- 가짜 응답으로 수집 3회:
  - 1회차: 신규 저장, 두 키워드에 걸린 기사는 한 건으로 저장되고 키워드 2개 연결, 이미 있던 기사에는 키워드만 추가
  - 2회차(같은 결과): 전부 "중복"으로 처리, 기사 수 변화 없음
  - 3회차(중간 차단): 앞 키워드까지 저장, 남은 키워드 건너뜀, 요청 로그에 차단 줄 기록
- 내보내기: 열 구성이 예전 CSV와 같고 원본 165건의 값이 그대로 들어 있음
- 다른 CSV 합치기: 겹치는 기사는 키워드만 추가, 새 기사만 저장
- 감성지수 열이 없는 예전 형식 CSV는 옮기지 않고 `repair_csv.py`를 먼저 돌리라고 안내 후 멈춤


수집(`run_collect.bat`)과 서버(`uvicorn start:app`) 실행 방법은 그대로다.

### 6-7. 주의할 점

- `news.db`와 함께 `news.db-wal`, `news.db-shm`이 생길 수 있다. 수집·서버가 돌고 있을 때 쓰는 작업 파일이니 지우지 않는다.
- 폴더를 압축해서 옮길 때는 서버와 수집이 돌고 있지 않을 때 한다. (그러면 작업 파일 내용이 `news.db`에 합쳐져 있음)
- DB 내용을 엑셀로 보고 싶으면 `export_db_to_csv.py`. 직접 열어보려면 DB Browser for SQLite 같은 프로그램을 쓴다.
- 내보낸 CSV를 고쳐도 DB에는 반영되지 않는다.
